temporal-fmt
/

Format and parse Temporal with the tokens you already know.

yyyy-MM-dd in, string out. Bad input throws instead of quietly handing you garbage. Locale-aware, zero dependencies.

$npm install temporal-fmt
  • 100% coverage (c8)
  • 0 dependencies
  • Node 20+
  • Apache 2.0

Node 26 shipped Temporal without a string formatter. TC39’s position is to use Intl.DateTimeFormat and leave token-style formatting to userland. Fair enough, but if 'yyyy-MM-dd' is muscle memory from date-fns or Day.js, this exists so you don’t have to give that up.

Native on Node 26+. Below that, bring a polyfill or call setTemporal(). Locale-aware tokens need Node 20+ either way, and anything older is untested.

Only want format and parse? temporal-fmt-lite is a frozen snapshot of the 0.8.2 surface: the same two functions and locale support, without recurrence or business calendars. Security and correctness fixes only, no LTS promise. Moving up to the full package later is additive, not a rewrite.

Quick start

import { format } from 'temporal-fmt/format';
import { parse } from 'temporal-fmt/parse';

const date = Temporal.PlainDate.from('2026-08-04');
format(date, 'yyyy-MM-dd');                      // "2026-08-04"

parse('yyyy-MM-dd HH:mm', '2026-08-04 15:45');   // Temporal.PlainDateTime

format(temporal, formatStr) in, parse(formatStr, input) out. Same shape as date-fns or Day.js.

Import from the subpaths, not the bare package. The package is big on npm (locales, recurrence, calendars, an analyzer), but a bundler only ships what you call. Measured with esbuild, format alone is about 27KB via the subpath and about 68KB from the bare entry.

Providing Temporal

Node 26+: it’s native and picked up automatically.

Polyfill:

import 'temporal-polyfill/global'
import { format } from 'temporal-fmt/format';

Bring your own. Call setTemporal() once, before your first format() or parse(). It wins over a native or global Temporal, and calling it with no argument clears the override. Handy for libraries that don’t want to touch the global namespace.

import { Temporal } from 'temporal-polyfill/full';
import { setTemporal } from 'temporal-fmt';

setTemporal(Temporal);

Only functions that build a value from scratch need this: parse(), parseISO(), resolveZoned() and a few others. Functions that just read fields off an existing value (format(), compare(), add()) never touch the namespace.

Formatting

format(date, 'MMMM d, yyyy');            // "August 4, 2026"
format(dt, "MMM d, yyyy 'at' h:mm a");   // "Aug 4, 2026 at 3:45 PM"
format(zdt, 'yyyy-MM-dd HH:mm zzz');     // "2026-08-04 15:45 America/New_York"

Wrap literal text in single quotes. For a literal single quote, write ''. Using a token the value can’t support (HH on a PlainDate) throws a descriptive error instead of emitting undefined.

  • format(temporal, formatStr, options?) returns a string.
  • formatToParts(...) returns { type: 'literal' | 'token', value, token? }[], handy for styling individual pieces.
  • compileFormat(formatStr) pre-tokenizes once. Format strings are already LRU-cached (500 entries), so this mostly buys up-front validation: a bad string throws at compile time.

Parsing

parse() returns a PlainDate, PlainTime, PlainDateTime or ZonedDateTime, depending on which tokens are in the format. In TypeScript you’ll narrow the result with a type guard.

parse('yyyy-MM', '2026-08-04T15:45:30');          // throws: shape mismatch
parse('yyyy-MM-dd', '2026-02-30');                // throws: not a real date
parse('EEEE, yyyy-MM-dd', 'Monday, 2026-08-04');  // throws: it's a Tuesday

Other entry points: safeParse (returns { ok, value | error }), tryParse (value or undefined), parseToParts (matched groups with positions) and compileParser (precompiled, for repeated use).

Rules worth knowing

  • yy follows POSIX strptime: 00–68 is 2000–2068, 69–99 is 1900–1999.
  • hh/h without a throws, and so does mixing HH with hh.
  • HH with a is allowed and cross-checked: '13:05 PM' passes, '01:05 PM' throws.
  • a is case-insensitive. Month and weekday names are case-sensitive.
  • S to SSSSSSSSS go up to nanoseconds. Parse right-pads short input.
  • MMMM/MMM assume a 12-month calendar.

Ambiguity and lenient mode

When a glued numeric run has more than one valid split, parse throws. Zero-pad (MM/dd) or add a separator, or opt in:

parse('yyyy-Md', '2026-121')                              // throws: ambiguous
parse('yyyy-Md', '2026-121', { lenient: true })           // 2026-12-01

The lenient heuristic prefers the split where day ≤ 12, then falls back to the first valid split.

Offsets

Uppercase X/XX/XXX collapse +00:00 to Z. Lowercase never emits Z. On parse, an offset needs a full date and time and a zzz, because an offset is a UTC distance, not a time zone. If both are present they’re cross-checked and a mismatch throws. Range is -12:00 to +14:00, and sub-minute offsets only pass through xxx.

RRRR is the ISO week-numbering year, not the calendar year, and the two disagree around New Year: 2027-01-01 formats as ww RRRR → "53 2026".

Every token’s metadata (round-trip safety, locale and timezone sensitivity, supported types) is available through tokenInfo(name) or TOKEN_METADATA. yy isn’t round-trip safe because the century gets re-derived.

Locales

Pass a BCP 47 tag as options.locale. The default is 'en-US'.

format(date, 'MMMM d, yyyy', { locale: 'fr-FR' });   // "août 4, 2026"
format(dt, 'h:mm a', { locale: 'ja-JP' });            // "3:45 午後"

Named tokens (MMMM, MMM, EEEE, EEE, a) go through Intl.DateTimeFormat, so non-Gregorian calendars work when the value already carries one: date.withCalendar('hebrew') formats as "Av 21, 5786". Numeric tokens read fields directly and never touch Intl.

Digits

Numeric output is Western digits by default, whatever the locale. Opt in per call:

format(date, 'yyyy-MM-dd', { numberingSystem: 'arab' });   // "٢٠٢٦-٠٨-٠٤"
format(date, 'yyyy-MM-dd', { numberingSystem: 'auto', locale: 'bn-BD' });
parse('yyyy-MM-dd', '٢٠٢٦-٠٨-٠٤', { parseNumberingSystem: 'arab' });

The two options are separate on purpose: you may want localized digits out without expecting them back in. 'auto' uses the locale’s own system and falls back to 'latn' if it isn’t supported. Helpers: convertDigits, convertDigitsToAscii.

Custom vocabulary

Intl misses some cases, a 13-month Hebrew leap year being the usual one. registerLocaleVocab(locale, vocab) takes months, weekdays and day periods. registerLocale(locale, vocab) also takes quarters, eras, ordinals, duration units and relative-time wording. Validation is strict (wrong lengths, empty strings, duplicates, identical AM/PM all throw at registration), and registering clears that locale’s cache. getLocale and hasLocale read it back.

Durations

formatDuration(duration, formatStr, options?) takes a Temporal.Duration or a plain field bag. Every unit has numeric, short and long forms, and the short and long ones are plural-aware.

UnitNumeric / short / long
yearsy yy yyy → 2 / 2yr / 2 years
monthso oo ooo
weeks, daysw ww www, d dd ddd
hours, minutes, secondsh hh hhh, m mm mmm, s ss sss
millisecondsS SS SSS
formatDuration({ hours: 2, minutes: 30 }, 'hhh mmm')                       // "2 hours 30 minutes"
formatDuration({ hours: 2, minutes: 30 }, 'hhh mmm', { locale: 'de-DE' })  // "2 Stunden 30 Minuten"

Zero-value units are omitted unless you pass { showZeroValues: true }, and cleaning up leftover separators is on you. An explicit locale: 'en-US' isn’t the same as omitting it, because Intl spaces things differently ("2 hr" vs "2h").

Also: formatDurationToParts, parseDuration, parseISODuration, formatISODuration, balanceDuration, totalDuration, compareDuration, addDuration, subtractDuration, roundDuration (months and years need a relativeTo).

Relative time

formatDistance(today, yesterday)                         // "yesterday"
formatDistance(today, yesterday, { numeric: 'always' })  // "1 day ago"
formatDistance(today, today.add({ days: 2 }), { locale: 'fr-FR' })  // "dans 2 jours"
formatDistanceToNow(threeHoursAgo)                       // "3 hours ago"

The direction is date1 - date2, so positive means “in X” and negative means “X ago”. Units switch at 60 seconds, 60 minutes, 24 hours, 30 days and 365 days. Override any of them with { cutoffs }. The months cutoff is in days because a month has no fixed length, and non-monotonic or non-positive values throw. It accepts PlainDate, PlainDateTime and ZonedDateTime, and throws on PlainTime.

formatRelative and formatRelativeToNow give calendar labels (“yesterday”, “last week”) instead of counts.

Natural-language dates

parseRelative(input, referenceDate, options?) turns phrases into a PlainDate. English by default, plus es, fr and de.

const today = Temporal.PlainDate.from('2026-08-04');   // a Tuesday
parseRelative('next Tuesday', today)    // 2026-08-11
parseRelative('last Friday', today)     // 2026-07-31
parseRelative('in 3 days', today)       // 2026-08-07
parseRelative('March 5th', today)       // 2027-03-05
parseRelative('mañana', today, { locale: 'es-ES' })   // 2026-08-05

It handles weekday references, today/tomorrow/yesterday, “in 3 days” and “2 weeks ago”, and month-day with no year. The calls it makes on ambiguous input:

  • “next Tuesday” on a Tuesday is 7 days out. Use “this Tuesday” for the same week.
  • “March 5th” with no year means the next occurrence, so a past date rolls to next year.
  • A bare “5 days” with no “in” or “ago” throws, same strict contract as parse().

Diacritics are stripped before matching, so miercoles works. { fuzzy: true } fixes typos like tommorow using edit distance 2. It’s English-only, and pairing it with another locale throws instead of silently skipping the correction. Numbers are never corrected. Add your own language with registerRelativeGrammar.

Arithmetic, comparison and rounding

add(date, 3, 'days');        // or addDays(date, 3)
difference(a, b, 'hours');   // integer unit boundaries crossed
compare(a, b);               // -1 / 0 / 1
startOf(date, 'month');
getQuarter({ month: 8 }, { startMonth: 10 });   // 4, Apple's fiscal year
  • Arithmetic: add, subtract, difference, plus per-unit wrappers like addMonths and differenceInDays.
  • Comparison: isEqual, isBefore, isAfter, min, max, clamp, isBetween, isToday, isSameDay, isSameWeek, isWeekend and friends.
  • Rounding: round, floor, ceil, truncate.
  • Calendar: daysInMonth, isLeapYear, dayOfYear, weekOfYear, startOf, endOf, getQuarter.
Gregorian only. daysInMonth, daysInYear, isLeapYear, monthsInYear, dayOfYear, weekOfYear and weekYear use Gregorian rules and are wrong on other calendars. For those, read the Temporal object’s own properties (pd.daysInMonth).

Intervals and recurrence

const iv = interval(start, end, 'closed');   // or open, half-open-start, half-open-end
contains(iv, someDate);
overlaps(ivA, ivB);
formatRange(iv, 'MMM d');

const rule = { freq: 'weekly', interval: 1, count: 10 };
take(recurrence(startDate, rule), 5);
between(startDate, rule, rangeStart, rangeEnd);

Intervals also have intersection, union (null when they can’t combine), mergeIntervals and splitInterval. Where names clash with the date functions, the main entry exports intervalIsBefore, intervalDifference and so on.

Recurrence follows the RFC 5545 RRULE model: freq from secondly to yearly, interval, count, until, weekday and month-day constraints, exclusions. parseRRule and formatRRule read and write RRULE text, and the iterator has next() and previous().

Business calendars and holidays

These are two separate things. A business calendar covers weekends, working hours and half days. A holiday calendar is a set of specific dates. Compose them by passing the holidays into the business calendar’s options.

const holidays = createHolidayCalendar([
  { month: 1, day: 1, name: "New Year's Day" },
  { compute: (year) => ({ month: 5, day: lastMondayOf(year, 5) }), name: 'Memorial Day' },
]);

const cal = createBusinessCalendar({ /* weekend days, holidays, hours, half days */ });
addBusinessDays(cal, someDate, 5);

Business: isBusinessDay, addBusinessDays, subtractBusinessDays, differenceInBusinessDays, nextBusinessDay, previousBusinessDay. Holidays: isHoliday, holidaysBetween, nextHoliday, previousHoliday (capped at five years each way).

Country holiday datasets are out of scope. createHolidayCalendar is the abstraction, and filling it is your job.

Time zones

resolveZoned(
  { year: 2026, month: 3, day: 8, hour: 2, minute: 30 },
  'America/New_York',
  { disambiguation: 'compatible' }   // or earlier, later, reject
);

resolveZoned makes you pick what happens in a DST gap or overlap. possibleInstantsFor returns none for a gap, two for an overlap, one otherwise. Also: getTimeZone, getOffset, getNextTransition, getPreviousTransition and getTransitions(start, end).

isDST compares the current offset to January’s. That’s right in the Northern Hemisphere and can read backwards in the Southern one, where January is summer.

Serialization

Each format has a parse and a format function: ISO 8601 (parseISO), RFC 3339, RFC 2822, HTTP-date, and SQL DATETIME/TIMESTAMP. Epoch helpers cover seconds, milliseconds, microseconds and nanoseconds both ways (fromUnixSeconds, toUnixMilliseconds, …).

parseISO('2026-08-04T15:45:30Z');
fromUnixMilliseconds(1754321130000);

Errors and type guards

Errors are TemporalFmtError subclasses carrying code, input, format, token, position, expected, actual and reason.

ClassFires when
FormatSyntaxErrorUnterminated quote, over-long format string
UnknownTokenErrorUnrecognized letter run
ParseMismatchErrorInput doesn’t match the format’s shape
InvalidDateError / InvalidTimeErrorFeb 30, hour 25, or a weekday or quarter that contradicts the date
InvalidOffsetError / InvalidTimeZoneErrorBad offset (outside -12:00 to +14:00) or unknown zone
InvalidCalendarError / InvalidLocaleErrorUnsupported calendar, bad BCP-47 tag or numbering system
AmbiguousInputErrorMore than one valid reading
InvalidDurationErrorNot ISO 8601 grammar, or a non-finite field

Messages you’ll probably hit

  • “no valid pattern matches the format string and input shape”: usually a missing separator, a wrong digit count, or zzz grabbing something that isn’t a zone ID.
  • “token X requires Y, which this Temporal object doesn’t have”: like HH on a PlainDate.
  • “incomplete date”: year, month and day must all be present together.
  • “X is ambiguous”: add a separator, zero-pad, or use { lenient: true }.
  • “falls in a DST gap”: pick another time, or pass a disambiguation to resolveZoned.

Type guards (isPlainDate, isZonedDateTime, …) and matching assert* functions cover every Temporal type and narrow what parse() returns. If you still depend on plain-Error identity, temporal-fmt/legacy is a deprecated compatibility layer with no removal date. Don’t use it in new code.

Tooling extras

analyzeFormat, explainFormat, validateFormat and tokenInfo inspect a format string before you use it. createConfig bundles defaults (locale, zone, rounding and so on). createFormatter adds custom tokens. getAutocompleteData, getHoverDocs and getInlineDiagnostics exist for editor tooling.

Migrating from Day.js or date-fns

X x (unix)not supported, use fromUnixSeconds / fromUnixMilliseconds

MMMM MMM MM M, HH H mm m ss s and all the add, isBefore, isToday style functions keep their names.

What will bite you

  • Parsing is strict. Day.js silently picks one reading of ambiguous input. This throws.
  • Cross-field validation. A wrong weekday label throws.
  • No “now” fallback. Missing input doesn’t become the current time.
  • Types matter. format(plainDate, 'HH:mm') throws. Day.js would quietly use 0.
  • It’s Temporal-native, not Date-native. Convert at the boundary.
  • Locales are per call (BCP-47 strings), not global like dayjs.locale('fr').
  • Audit anything leaning on Day.js’s customParseFormat, since that plugin parses leniently.

You can migrate file by file by wrapping both libraries behind one function and dropping the wrapper once nothing uses the old path.

The smoke runner packs and installs the package, checks every public subpath in CJS and ESM, and runs type probes under both bundler and nodenext resolution. npm run test:smoke     # packed-package smoke suite
npm run test:browser   # Playwright against dist/

Hacking on it: git clone, npm install, npm run build, npm run test:all. The build needs TypeScript 7.0.2+, and .d.ts files come from a separate tsc pass because tsup’s dts step isn’t stable on 7.x.
