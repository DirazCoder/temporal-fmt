Errors and type guards

Errors are TemporalFmtError subclasses carrying code, input, format, token, position, expected, actual and reason.

ClassFires when
FormatSyntaxErrorUnterminated quote, over-long format string
UnknownTokenErrorUnrecognized letter run
ParseMismatchErrorInput doesn’t match the format’s shape
InvalidDateError / InvalidTimeErrorFeb 30, hour 25, or a weekday or quarter that contradicts the date
InvalidOffsetError / InvalidTimeZoneErrorBad offset (outside -12:00 to +14:00) or unknown zone
InvalidCalendarError / InvalidLocaleErrorUnsupported calendar, bad BCP-47 tag or numbering system
AmbiguousInputErrorMore than one valid reading
InvalidDurationErrorNot ISO 8601 grammar, or a non-finite field

Messages you’ll probably hit

  • “no valid pattern matches the format string and input shape”: usually a missing separator, a wrong digit count, or zzz grabbing something that isn’t a zone ID.
  • “token X requires Y, which this Temporal object doesn’t have”: like HH on a PlainDate.
  • “incomplete date”: year, month and day must all be present together.
  • “X is ambiguous”: add a separator, zero-pad, or use { lenient: true }.
  • “falls in a DST gap”: pick another time, or pass a disambiguation to resolveZoned.

Type guards (isPlainDate, isZonedDateTime, …) and matching assert* functions cover every Temporal type and narrow what parse() returns. If you still depend on plain-Error identity, temporal-fmt/legacy is a deprecated compatibility layer with no removal date. Don’t use it in new code.
